# 外屏时钟 v1.4.0 · 重建设计说明

> 重建时间：2026-10-13 · 目标机型：小米 18 Fold（中折叠 / 阔折叠；本机 2608BPX34C / HyperOS，Android 17 / SDK 37）
> 原版：v1.3.7 (versionCode 15) · 新版：**v1.4.0 (versionCode 16)**

---

## 一、先说结论：充电合盖自动开启，到底能不能真正实现？

> **已经不只是"能"了——2026-10-13 晚上在你手机上真跑通了：合盖 → 插电 → 外屏亮起时钟；拔电 → 自动收起。**
> 完整的实测日志和证据在第七点五节。

**能实现，但 v1.3.7 那套写法注定失败；而且它不是「装上就灵」，需要用户手动打开 2~3 个系统开关。**

这个功能要拆成四件事，每一件事的可行性完全不同：

| 环节 | 能不能做到 | v1.3.7 做得怎么样 |
|---|---|---|
| ① 检测「插上电了」 | ✅ 一定能 | 能，但服务经常根本不在跑 |
| ② 检测「合盖了」 | ⚠️ 能，但有坑 | **写错了**：等传感器事件，而合盖时 CPU 已挂起 |
| ③ 把界面亮到外屏上 | ❗**真正的瓶颈** | 依赖最脆弱的那条路（后台启动 Activity） |
| ④ 长期一直有效 | ❌ 完全没做 | 没有开机接收器，重启即永久失效 |

所以答案是：**「充电合盖自动开启」不是一个能不能实现的问题，而是一个「在哪一层实现才不会被系统掐死」的问题。** 下面逐条说清楚。

---

## 二、四件事逐条拆解

### ① 检测充电 —— 可以，但有前提

- `ACTION_POWER_CONNECTED` **不能**用清单里的 `<receiver>` 收。
  我核对了官方「隐式广播例外清单」（Android 17 文档，2026-05-18 更新）：例外里有 `ACTION_BOOT_COMPLETED`、`ACTION_TIMEZONE_CHANGED`、`ACTION_USB_*`、`ACTION_MEDIA_*` 等等，**没有 `ACTION_POWER_CONNECTED`**。
  targetSdk ≥ 26 之后，清单声明的充电广播收不到。必须有一个**活着的组件**（前台服务）在运行时动态注册。
- v1.3.7 确实是动态注册的（`AutoLaunchService$powerReceiver$1`），这点没错。
- 但**服务本身只在 `MainActivity.onCreate()` 里被拉起一次**，而且只在 `Prefs.autoLaunch` 为真时。所以：重启手机 → 服务没了 → 之后插多少次电都没反应。

**结论：技术可行，但必须配一个开机接收器 + 前台服务保活。**

### ② 检测合盖 —— 能，但 v1.3.7 的写法有硬伤

- 本机用的是 `Sensor.TYPE_HINGE_ANGLE`（铰链角度，0=合上，180=摊平）。
- **关键坑：它不是 wake-up 传感器。** 合盖之后屏幕熄灭、SoC 挂起，传感器回调**不会把进程唤醒**。所以「常驻监听、等合盖事件来了再动作」这种写法，在真机上会经常哑火——尤其顺序是「先合盖、后插电」的时候。
- **正确做法**：把触发权交给「插电广播」（它会唤醒进程），然后**主动去要一次当前角度**：临时切到高频采样，拿到第一帧就判断、超时就用缓存值兜底。
- 新版本 `HingeMonitor.request()` 就是这个逻辑。

**结论：技术可行，但要改成「主动取样」而不是「被动等事件」。**

### ③ 把界面亮到外屏上 —— 这里是瓶颈，有两条例外的路

Android 10+ 有 **后台启动 Activity（BAL）限制**。我核对了官方文档，例外条件包含：

> The app has the SYSTEM_ALERT_WINDOW permission granted by the user.

也就是说，`startActivity()` 想从后台成功，**必须有「悬浮窗」权限**。v1.3.7 要悬浮窗权限是对的（它的设置页也在催），但它把宝全押在这条路上。

而在这台 HyperOS 机器上，还有第二道闸：**MIUI/HyperOS 专有的「后台弹出界面」**。这是 AOSP 之外的厂商限制，即使有 `SYSTEM_ALERT_WINDOW`，没开这个开关照样弹不出来。系统不提供任何 API 查询或申请它，只能把用户送到设置页。

所以真正稳的是**另一条路**：

> **直接把时钟做成 `TYPE_APPLICATION_OVERLAY` 悬浮窗，从服务里加上去。**

「加一个悬浮窗」**不是**「后台启动 Activity」，完全不受 BAL 约束，也不吃「后台弹出界面」那一套。只要悬浮窗权限给了，服务活着，就能亮。

而且这条路上还有个额外的好处：折叠时主屏是灭的，**必须把窗口加到「当前亮着的那块屏」上**——用 `DisplayManager` 挑一块 `STATE_ON` 且非私有的显示器，再 `createDisplayContext()` 拿 `WindowManager`，才能加到外屏去。v1.3.7 的 `OverlayClock` 只是设置页里的一个「测试」按钮，没被用在自动路径上。

**新版本把悬浮窗定为默认路径，「启动界面」降级为兜底。**
另外，真要启动界面时，targetSdk 34+ 还有一个 AOSP 认可的技巧（文档原文：creator 可以「显式委托」自己的后台启动特权）：

```
PendingIntent + ActivityOptions.MODE_BACKGROUND_ACTIVITY_START_ALLOWED
```

本应用同时是 creator 和 sender，而自己持有 `SYSTEM_ALERT_WINDOW` → 符合 doc 里的放行条件。v1.3.7 直接 `startActivity()`，把这条本可以用的路子浪费了。

### ④ 长期有效 —— v1.3.7 完全没做

我从合并清单里逐条核对过，**v1.3.7 没有 `RECEIVE_BOOT_COMPLETED` 权限，也没有任何开机接收器**。

它自己的 README 里也写着：

> - 系统重启后需手动打开一次 App，自动弹出才会恢复

一个「充电就自动亮」的功能，重启一次就永久失效——这是最致命的一条。

新版本加了 `BootReceiver`（`BOOT_COMPLETED` / `MY_PACKAGE_REPLACED` / `USER_UNLOCKED`）。

## 三、还有一个 v1.3.7 完全不知道的事：HyperOS 的外屏是有白名单的

这是这次重建挖出来最有价值的东西。

我去 GitHub 上找同类问题的解法，找到了 **[parallelcc/MixFlipMod](https://github.com/parallelcc/MixFlipMod)**（面向小米 MIX Flip / Flip 2 的外屏增强模块，Xposed）。**本项目用的是 18 Fold，但外屏白名单是 HyperOS 共用的一套属性**，这个模块印证了机制。它的功能第一条就是：

> 系统框架：**解除外屏应用限制**

也就是说，**HyperOS 默认不让随便什么应用跑到外屏上**，需要系统放行。它靠 Xposed hook 系统服务强制放行：

```kotlin
val props = arrayOf("miui.continuity.policy",
                    "android.window.PROPERTY_COMPAT_ALLOW_SMALL_COVER_SCREEN")
// getPropertyIntByApplication 返回 5 / 1  →  所有应用都允许上外屏
```

然后我直接对**这台机器的系统框架和系统 APK** 做了取证：

1. `/system/framework/framework.jar` 里确实存在这些标识符：
   `COMPAT_SMALL_COVER_SCREEN_OPT_IN`、`android.window.PROPERTY_COMPAT_ALLOW_SMALL_COVER_SCREEN`、
   `miui.supportFlipFullScreen`、`com.miui.fliphome`。
2. 扫描 391 个系统 APK，找到了**真实声明样例**。其中 `MiuiScanner` 的清单里有：

```xml
<property android:name="android.window.PROPERTY_COMPAT_ALLOW_SMALL_COVER_SCREEN" android:value="1" />
```

`MIUIDeskClock`、`MIUIGallery`、`Settings`、`MIUIWeather` 等 40 多个系统 App 里还有：

```xml
<property  android:name="miui.continuity.policy"        android:value="5" />
<meta-data android:name="miui.supportFlipFullScreen"    android:value="0" />
```

（`miui.supportFlipFullScreen`：0 = 全屏铺满，1 = 不缩放，2 = 自定义缩放。）

**v1.3.7 这三条一条都没写。** 这很可能就是它「合盖以后外屏什么都不发生」的另一半原因——不是没弹出来，而是**系统根本不允许它在外屏上出现**。

新版本已经把这三行原样写进 `<application>`。

> ⚠️ **诚实的保留意见**：上面这三条是从**系统 App** 里取证到的写法。第三方 App 声明同样的属性，HyperOS 是否同样采纳，**我没有办法在不动手安装验证的情况下断言**。这是一个必须实机验证的点（见第六节）。但至少这是有据可依的正确做法，而不是拍脑袋。

## 四、v1.3.7 硬伤清单 → 逐条修复对照

| # | v1.3.7 的问题 | 证据 | v1.4.0 的修复 |
|---|---|---|---|
| 1 | 重启后自动弹出永久失效 | 清单里没有 `RECEIVE_BOOT_COMPLETED`，没有开机接收器 | 新增 `BootReceiver`，开机 / 覆盖安装 / 解锁都自动拉起服务 |
| 2 | 靠「等合盖事件」，合盖时 CPU 已挂起 → 哑火 | `TYPE_HINGE_ANGLE` 非 wake-up 传感器 | `HingeMonitor.request()`：被插电广播唤醒后**主动取样**，1.5s 超时；20s 兜底轮询 |
| 3 | 只走 `startActivity()`，撞 BAL + HyperOS「后台弹出界面」两道闸 | 官方 BAL 例外表；MIUI 厂商限制 | 默认改成**悬浮窗**（不触发 BAL）；启动界面时用 `MODE_BACKGROUND_ACTIVITY_START_ALLOWED` 显式委托特权 |
| 4 | 没有声明 HyperOS 外屏白名单 | 系统 APK 取证（见第三节） | 补上 `PROPERTY_COMPAT_ALLOW_SMALL_COVER_SCREEN` / `miui.continuity.policy` / `miui.supportFlipFullScreen` |
| 5 | 悬浮窗只能加在默认屏上 | `OverlayClock` 没选显示器 | 用 `DisplayManager` 挑当前亮着的那块屏，`createDisplayContext` 后挂窗口 |
| 6 | `StandbyDreamService` 在清单里声明了两遍 | 旧机构建日志就是这条 warning | 删掉重复的一份 |
| 7 | `debuggable=true` 被当成「release」发出去 | 合并清单 `android:debuggable="true"` | 不再带 debug 标记 |
| 8 | 主界面强制 `sensorLandscape`，在外屏（竖屏）上姿态是错的 | 清单 `screenOrientation="6"` | 改成自适应：横屏左右分栏、竖屏上下堆叠；方向可在设置里选「自动/横屏/竖屏」 |
| 9 | 亮度硬编码 `0.04f`，白天外屏几乎看不见 | `MainActivity.onResume` 写死 | 变成可调项（1%~100%），默认 6% |
| 10 | 「拔电即退出」只写在注释里，代码没做 | `maybeAutoExit()` 只判断角度 | 拆成两个独立开关：展开关闭 / 拔电关闭 |
| 11 | 读不到传感器时 `angle` 永远是 -1，既不显示也永不退出 | `angle` 初值 -1 | 无传感器时降级为「充电即显示」，并有明确开关 |
| 12 | 设置页只说「去授权」，用户不知道到底哪一步没生效 | 只有文案 | 新增**自检面板**：服务状态 / 充电状态 / 铰链角度 / 悬浮窗权限 / 通知权限 / 电池优化 / 悬浮窗在几号屏 / 上次触发时间与原因，实时刷新 |
| 13 | 21.3 MB（Compose 全家桶） | 原 APK | 纯 Java + 自绘 View，**零第三方依赖**，预计几百 KB |
| 14 | 失败时完全静默 | 无日志无反馈 | 每次 `show()` 失败都写 Log 并带上是哪一步（权限？模式？），通知里也能看到当前状态 |

| 15 | 包名 `com.example.foldclock` | 发布物料里自己也提了 | **保持不动**（见下方说明，改包名的代价和收益见第七节） |

## 六、怎么构建、安装、验证

### 构建 —— 已经实测跑通了

这台机器上原本没有可用的 JVM（Termux 在别的应用私有目录里，读不到）。这次顺手把一套 **JDK 17 + aapt2 + d8 + apksigner** 装进了应用私有目录（`/data/user/0/com.deepseek.harness.compat/files/`），所以**不需要 Termux、不需要 root/Shizuku**就能编译。

一条命令：

```sh
sh /sdcard/Download/FoldClock/源码重建/build.sh
```

脚本会自动：找到工具链 → 找到 android.jar → 找到/生成签名密钥 → aapt2 → javac → d8 → 打包 → 签名 → 复制到 `/sdcard/Download/`。

**实测结果（2026-10-13 21:45）：**

```
[1/5] aapt2 compile        OK
[2/5] aapt2 link           OK
[3/5] javac                OK（69 个 class）
[4/5] d8 → classes.dex     OK（65,564 字节）
[5/5] 打包 + 签名           OK
✅ build/FoldClock-v1.4.0.apk  58,060 字节
   签名证书 SHA-256: c61fd50a33432fbcad88ba5935100cd7d5b343e08651dbf9c637f20fd0647cca
```

编译期间只暴露出 **1 个真实错误**（`NotificationChannel.setLights(int,int,int)` 不存在，改成 `enableLights(false)`），已经修掉。

体积对比：**21.3 MB → 58 KB**。

我还把编译产物拆开核对过：清单里 `PROPERTY_COMPAT_ALLOW_SMALL_COVER_SCREEN = 1 (int)`、`miui.continuity.policy = 5 (int)`、`miui.supportFlipFullScreen = 0` 三条都**以正确的类型**落了进去，和系统 App 里的写法完全一致；`classes.dex` 里 8 个关键类也都在。

### 签名

原来的 release 密钥（`foldclock-release.jks`）没有备份出来，`签名/` 目录是空的，**无法再签出能覆盖 v1.3.7 的包**。所以这次生成了一把专用的新密钥：

| | |
|---|---|
| 文件 | `签名/foldclock.jks`（同时存于 `files/keystores/foldclock.jks`） |
| 别名 | `foldclock` |
| 口令 | 不写进仓库；构建时通过 `KSPASS` 环境变量传入 |
| SHA-256 | `C6:1F:D5:0A:33:43:2F:BC:AD:88:BA:59:35:10:0C:D7:D5:B3:43:E0:86:51:DB:F9:C6:37:F2:0F:D0:64:7C:CA` |
| 有效期 | 到 2056 年 |

**请把它复制到网盘/电脑，并改掉口令。** 丢了就再也发不了升级版。

### 安装

因为签名变了，**必须先卸载 v1.3.7**：

1. 长按桌面上的「外屏时钟」→ 卸载（设置会一起丢，没办法）
2. 文件管理器点 `/sdcard/Download/FoldClock-v1.4.0.apk`
3. 若有「未知来源」提示，允许一次；MIUI 的「未经安全检测」选继续安装

### 验证顺序（建议照这个来，能最快定位问题）

1. 打开 App → 进设置 → 看**自检面板**：
   - 悬浮窗权限 → 去授权
   - 通知权限 → 去授权
   - 电池优化 → 设为无限制
   - （小米）自启动 → 打开
   - 先**只测悬浮窗**：点「测试悬浮窗显示」，确认时钟出现在**外屏**上。
     - 如果出现在内屏而不是外屏 → 把自检面板里「显示器」那一行拍下来。
     - 如果完全没出现 → 大概率是 HyperOS 的外屏限制（第三节），去系统「外屏」设置里看能不能手动把「外屏时钟」加进去。
2. 悬浮窗通了之后，打开「自动在外屏启动时钟」，合盖 → 插电。
3. 还不行就把「显示方式」改成**仅悬浮窗**（彻底绕开「后台弹出界面」）。
4. 最后可以试**设为系统屏保**：唯一一条「系统自己拉起来、不需要任何特权」的路。

**出问题抓日志**，过滤 `FoldClock`：

```
adb logcat -s FoldClock/Svc FoldClock/Overlay FoldClock/Hinge
```

## 七、老实说：哪些验证过了，哪些还没有

### 已经验证过（不是嘴上说说）

- **代码能编译**：JDK 17 + 你机器上那个裁剪过的 `android.jar`，`javac` 零错误通过，`d8` 出 dex，`apksigner` 签名验证通过。
- **清单正确**：把编译出来的 APK 里的二进制清单解析出来逐条核对过，外屏三件套的类型和取值与系统 App 一致。
- **没有第三方依赖**：68 个 import，全部来自平台；`androidx` 一个都没有。
- **静态交叉检查**：15 个类全部通过 Java 语法解析；所有 `R.*` 资源引用都能对上；项目内部的方法调用与参数个数、平台 API 的成员引用都逐一核对过。

### 还没验证（只能装上才知道）

1. ~~第三方 App 声明 `PROPERTY_COMPAT_ALLOW_SMALL_COVER_SCREEN` 是否被 HyperOS 采纳。~~ → **已实测通过，见第九节。**
2. ~~悬浮窗能不能真的挂到外屏（cover display）上。~~ → **已实测通过，见第九节。**

### 实测中揪出来并修掉的 7 个问题

这一节才是实机验证的价值——有些东西光看代码根本发现不了。

1. **日历面板整个不显示**（最严重）
   根因：我把「横屏/竖屏该用哪种布局」的判断放在了 `onSizeChanged()` 里，而它是在**布局完成之后**才回调的；在那里改 LayoutParams 要多走一轮布局，实际没生效，日历被分到了 0 宽度。
   修法：挪到 `onMeasure()` 里，在测量之前就把方向和 LayoutParams 定下来。
   *这个问题在真机上 100% 复现，但纯静态检查永远发现不了。*

2. **误判充电状态**（你反馈的）
   根因：`readCharging()` 除了看 `EXTRA_PLUGGED`，还看了 `EXTRA_STATUS == CHARGING/FULL`。那个状态位在拔线后可能残留，于是「没插电也一直当成充电中」。
   修法：只认 `EXTRA_PLUGGED != 0`（充电器是否插着），这才是「插电」的语义。

3. **反复弹窗**
   根因：用户手动点掉之后，20 秒一轮的兜底轮询又会把它弹回来。
   修法：加了「用户已手动关闭」抑制位；只有**插拔电**或**折叠状态真的变化**（展开↔合盖）才解除抑制。另外把「拔电自动关闭」的默认值改成开。

4. **插电广播到达时读到旧的 sticky 状态**（偶发，最难查）
   现象：同一个操作，有时能弹有时不能。
   根因：`ACTION_POWER_CONNECTED` 广播先到，此时再去读 sticky 的 `ACTION_BATTERY_CHANGED`，读到的可能还是「没插电」的旧值，于是这一次就被判成未充电而错过。
   修法：电源事件直接采信广播带来的状态，不再回头去读 sticky；其余场合（开机、轮询）才重新读取。
   顺手在 `evaluate()` 和铰链回调里加了完整的状态日志，以后这类问题一眼可见：
   `evaluate(power-connected) charging=true auto=true dismissed=false lastFolded=false visible=false`

5. **主界面没有设置入口**
   原版右上角有个齿轮，我第一版漏了。补回来，并且往内让开了挖孔/圆角区（原版那个齿轮贴在最边缘，很难点到）。

6. **悬浮窗没盖满屏，底部露出一条系统桌面**（你反馈的）
   现象：外屏 1712 高，但窗口只拿到 **1657** —— 系统把状态栏/导航栏的 inset 从窗口高度里扣掉了，底下那 55px 就盖不住，直接露出桌面。
   证据：`layout 1168x1657 竖`（外屏是 1168x1712）。
   修法：给窗口加 `setFitInsetsTypes(0)` + `setFitInsetsSides(0)`，不参与任何 inset 计算。修完日志变成 `layout 1168x1712 竖` / `layout 1712x1168 横`——**正好等于屏幕尺寸，整屏铺满**。

7. **日历固定画 6 行，多出来的那行看着像留白**（你反馈的）
   10 月只需要 5 行（10/1 是周四，31 天），第 6 行整行都是 11 月的日期，渲染成暗灰，视觉上就是底部一大块空。
   修法：按 `ceil((前置空格 + 当月天数) / 7)` 算出真实需要的行数，只画这么多行，格子高度随之变大。

> 另外说明：测试时我用 `dumpsys battery set ac 1` 伪造过充电状态来触发流程——这就是你看到「系统也显示在充电」的原因，是我的测试手段，不是 App 的 bug。已经 `dumpsys battery reset` 还原。
> 测试期间还临时改过 `accelerometer_rotation` / `user_rotation` 来验证旋转，也都已经改回自动旋转。

## 七点六、排版最终定稿：只有横屏

来回试了几版之后定下来的取向：

### 规则

| 外屏状态 | 行为 |
|---|---|
| **横屏** | 显示：左时钟、右日历，铺满整屏 |
| **竖屏** | **什么都不显示**（外屏立着的时候不亮时钟） |

- 只有**一套**排版，不再维护竖屏上下堆叠那一套（省掉一份比例要调）。
- 竖屏不显示，所以也不需要「把横屏内容转 90°」这种兜底。
- `MainActivity` 用 `SCREEN_ORIENTATION_SENSOR_LANDSCAPE`，系统只决定横屏的左右朝向。
- 悬浮窗跟着外屏旋转；服务注册了 `DisplayManager.DisplayListener`，屏幕一转就重新判定——
  横过来立刻亮、竖过去立刻收。

### 判定「是不是横屏」用哪个 API（踩过的坑）

`Display.getWidth() / getHeight()` 返回的是**面板的原始尺寸**，不随旋转变化，
拿它判断会把外屏永远当成竖的。必须用 `Display.getSize(Point)` —— 它按当前旋转给尺寸。
日志里能直接看到判定过程：

```
I FoldClock/Overlay: display 0 size=1712x1168 rotation=1 -> 横     ← 亮起
I FoldClock/Overlay: display 0 size=1168x1712 rotation=0 -> 竖     ← 不显示
I FoldClock/Svc: evaluate(power-connected) 当前屏幕是竖的，不显示
```

### 日历占面板高度的比例

`HEIGHT_BUDGET = 0.60f`：日历内容块占所在面板高度的 60%，其余留成黑边。
这是从实机截图一版一版比出来的（0.42 太小、0.90 太满、0.72 横屏仍偏空），最终取 60%。
四周基础留白 `PAD_RATIO = 0.070f`，字号相对列宽 `WIDTH_FACTOR = 0.66f`
（旧版 v1.3.7 的数字约占列宽 72%，取 66% 是保证两位数的「28」也放得下）。

这些常量都带注释写在 `CalendarPanelView` 顶部，以后要微调直接改那三个数就行。

## 九、v1.4.1：把「合盖」判定从铰链角度换成显示状态（2026-10-14 晚）

### 症状

### 现场


而 `foldAngleMax` 默认 30° —— 系统说 FOLDED、本 App 说「已展开」，两套判定打架。

- 能看到两块屏 → 面积大的那块是内屏，内屏不亮 ⇒ 合盖。

  外屏最小边 1168px ≈ 425dp，内屏 1672px ≈ 608dp，以 550dp 为界。
- 铰链只留在日志里当参考值（`hinge(参考)=`），不参与判定；
  设置项改成「忽略折叠判定，充电即显示」，语义不变。

## 十、v1.4.2：「横屏时钟」的最终判定 —— 只看手机姿态（2026-10-14 深夜）

### 目标

用户给的两条目标姿态（都是微开、立在桌上、外屏横屏）：**A 字形**、**L 字形**。
只有满足条件才显示；竖着拿、平躺都不显示，而且**显示中一转到竖屏 / 平放就立刻退出**。

### 最终判定链

| 条件 | 实现 |
|---|---|
| 插着电 | `ACTION_POWER_CONNECTED` + sticky 电池状态 |
| 合盖（还在用外屏） | `OverlayClock.isCoverScreenOnly()`：只看得到外屏那块 = 合盖 |
| **手机横着放** | `PostureMonitor`（重力）：`|gy| ≥ |gx|` → 竖(0/180)，否则横(90/270)；`|gz| > 9.2` 且最大 → 平放，判不出来(-1) |
| 立刻退出 | 姿态一变（400 ms 去抖）回调服务重新判定 |
| 排版 | **只有横屏一套**（左时钟、右日历）；屏幕被前台 App 锁成竖屏时，用「舞台」把横屏尺寸的内容整体转 90°/270° 铺满 |

### 踩过的坑（都值得记下来）

1. **`Surface.ROTATION_*` 是枚举值 `0/1/2/3`，不是度数。**
   直接拿它做角度减法，差值算出来是 `1`，被「必须是 90 的倍数」那条判断归零 → 舞台不转 →
   屏幕上画出**竖屏时钟**。必须先 `×90` 换成度数再算。同一类错误还导致过「只有一个朝向」：
   早期代码把差值兜底成固定 90°，A 形和 L 形差 180°，必然有一个是倒的。
2. **外屏方向 ≠ 手机姿态。** 外屏方向是「谁在前台谁说了算」：桌面等竖屏锁定界面在前台时，
   外屏永远 `rotation=0`（实测 `displays=0:ON`、`1168x1712`），手机横着立在桌上也不转。
   所以判定必须看重力，不能看 `Display.getRotation()`。
3. **平放阈值别放太宽。** 一开始 `|gz| > 8.0`（≈离水平 35° 以内都算平躺），把 L 形稍微躺一点
   也吞了 → 时钟莫名退出。收到 `9.2`（≈20°）、噪声下限 `4.0 → 3.0` 后正常。
4. **HyperOS 的折叠策略不归 App 管**：合得不够，系统会启用内屏、外屏熄灭。
   这时 App 就不是「只亮着外屏」了，必须收掉 —— 否则会挡住内屏。
5. 更新 APK 后常驻服务不会自己回来：HyperOS 的「自启动」没给，`MY_PACKAGE_REPLACED` 会被拦掉
   （`MIUIOP(10008): ignore`），得手动打开一次 App，或去设置页把「自启动」给它。

### 实测

```
22:41:38.422  FoldClock/View: stage 1712x1168 rot=0 (desired=3 display=3)   ← 屏幕本身横屏，不用额外转
22:41:40.111  FoldClock/Svc: evaluate(display-changed) 手机不是横着放的（姿态=0），不显示
22:12:18.997  FoldClock/View: stage 1712x1168 rot=90 (desired=1 display=0)  ← 屏幕锁成竖屏，内容整体转 90°
```

### 已知未解决

L 字形在某些角度下画面方向仍不理想（用户决定不再为它调整）。正常横屏 + A 字形已可用。

## 十一、v1.4.3：出现/退出过渡动画 + 一个 HyperOS 的真坑（2026-10-14 深夜）

### 动画（按 iPhone 息屏时钟的节奏定的）

**出现**

| 时刻 | 动作 | 为什么 |
|---|---|---|
| 0 ms | 窗口挂上，alpha=0，亮度 = 当前屏幕亮度 | 亮度从当前值起步，才不会"亮一下再变暗" |
| 0→400 ms | 根视图 alpha 0→1 + 舞台 0.97→1.0 | 淡的是**根视图**，连黑底一起淡，不会先闪一层黑；缩放只给内容层，黑底不缩，边缘不会露出桌面 |
| 500 ms | 才开始压暗 | 先让时钟以舒服的亮度淡进来 |
| 500→2300 ms | 亮度用 **1.8 秒**缓入缓出沉到设定值 | 早期版本 320 ms 内直接掉到 6%，实机反馈"突然变亮再变暗"，改成"像床头钟一样慢慢沉下去" |

**退出**

- 根视图 alpha→0 + 舞台 1.0→0.985，**450 ms** 缓入缓出（原来 200 ms，用户反馈"退出有点快"）
- 亮度同步升回插电前的值 —— 不在 6% 亮度下淡掉
- 动画结束才 `removeViewImmediate`，另有 **+150 ms 兜底**：动画回调万一被系统吞掉，窗口不会挂在那儿

**工程细节**

- 动画常量集中在 `StandByView.ENTER_MS / EXIT_MS`，改时长只动这两个数
- 换向时先 `cancel()` 正在跑的亮度 `ValueAnimator`（压暗到一半拔电，回亮会从当前实际亮度接着走，两个动画不打架）
- 动画全部包 `try/catch`：出错退化成「直接出现 / 直接消失」，绝不影响显示逻辑本身
- 退出动画没播完又被要求显示 → 先立刻摘掉旧窗口再挂新的，不会出现"以为在显示其实没挂"

### 真坑：HyperOS 的 Greezer 会拦掉插电广播

现象：功能都改好了，插电还是不弹窗，而且**日志里连 `POWER_CONNECTED` 都没有**——不是 App 判定问题，是它压根没收到广播。

证据：

```
23:30:03.736 BroadcastQueue: Greezer Denial: sending Intent { act=ACTION_POWER_CONNECTED ... }
             due to receiver ProcessRecord{29204:com.example.foldclock} need cached broadcast
```

原因：MIUI/HyperOS 的 Greezer（后台冻结）在 App 于后台待久之后把它冻住，**动态注册的广播直接不投递**（进程也一起冻，连 20 秒兜底轮询都停）。判定读的是 MIUI 自己的「省电策略」，AOSP 那套都不够：

| 手段 | 结果 |
|---|---|
| `cmd deviceidle whitelist +pkg`（电池优化白名单） | 不够，照样被拦 |
| `am set-standby-bucket pkg active` | 不够 |
| `cmd appops set pkg 10008 allow`（MIUI 自启动 op） | 不够（但 UI 上「自启动」会显示已开） |
| **应用信息 → 省电策略 → 无限制** | ✅ 生效，`Greezer Denial` 消失 |

所以"时好时坏"的真相是：App 刚被打开过（前台、没冻）→ 能收到广播；在后台凉十几分钟 → 被冻 → 收不到。
**发布时要把这条写进 README**：装完必须去应用信息页把「省电策略」设为无限制、「自启动」打开。

## 十一、v1.4.4：锁屏路径 + 代码审查（2026-10-16）

### 锁屏场景（新能力）

锁屏时**悬浮窗画不到锁屏之上**（实测：窗口挂上了、屏幕上只有锁屏壁纸），全屏通知也被 HyperOS 压住，
只有 `showWhenLocked` 的 Activity 能盖住锁屏 —— 而从后台拉起它需要 MIUI 的
**「后台弹出界面」(appop 10021)** 与 **「锁屏显示」(10020)**。两条路都试、并撤销旧的全屏通知，
才能做到"每次插电都弹"（详见 `技术说明.md` 第十节）。

因此显示载体有两种，服务里用 `activityShowing` 明确区分：

- 悬浮窗（默认、解锁状态）：状态靠 `overlay.isAttached()` 判断 "窗口还在不在树上"；
- Activity（锁屏 / 悬浮窗失败退回）：没有窗口可查，用 2 分钟时间窗 + `ACTION_FINISH_UI`
  （服务收起时通知界面退场）+ `ACTION_USER_PRESENT`（用户解锁时自动退场）。

### 代码审查（12 处修复）

对全部 16 个类做了一次独立通读，修掉的问题里最值得记住的三条：

1. `OverlayClock.show()` 只检查 `view != null` 而不检查窗口是否还在树上 —— 窗口被系统摘掉后
   会"假装成功"（服务记 `visible=true`、屏幕全空、且以后永不重挂）。
2. `evaluate()` 的四处 early-return 跳过了"折叠态变化 → 解除 userDismissed"，
   于是「收起时钟 → 拿起来展开 → 重新合盖」这条最常见的序列里，时钟**再也不弹**。
3. `onDestroy` 没取消 700ms 后的 post-show 评估 —— 服务销毁后那次评估仍会在死对象上跑，
   可能挂出一块谁都摘不掉的窗口。

其余：通知文案/按钮改用服务的 `visible`、`armTicker()` 统一武装兜底轮询、
运行时申请通知权限、自检不再把"锁屏 Activity 正常显示"误报成 `E-SHOW-FAILED`、
反射隐藏 API 失败不再误判成"自启动没开"、防烧屏改成平移整个舞台（含齿轮）并平滑过渡。
