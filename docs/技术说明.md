# 技术说明

记录这一版重写时确认过的事实、踩过的坑和定下来的取舍。都是实机验证过的结论，
不是推测；凡是没验证的都会明确标出来。

---

## 一、「充电 + 合盖自动亮起」为什么难做

这个功能要拆成四件事，每一件的难点完全不同。

### 1. 检测「插上电了」

- `ACTION_POWER_CONNECTED` **不能**用清单里的 `<receiver>` 收。
  官方「隐式广播例外清单」里有 `ACTION_BOOT_COMPLETED`、`ACTION_TIMEZONE_CHANGED`、
  `ACTION_USB_*`、`ACTION_MEDIA_*` 等等，**没有 `ACTION_POWER_CONNECTED`**。
  targetSdk ≥ 26 之后，清单声明的充电广播收不到。
- 必须有**活着的组件**（前台服务）在运行时动态注册。

**结论：可行，但需要常驻前台服务 + 开机恢复。**

> **v1.4.3 补充：MIUI/HyperOS 上「动态注册」还可能被 Greezer 拦掉。**
> 现象是插电完全没反应，而且 `logcat` 里连 `POWER_CONNECTED` 都没有：
> ```
> BroadcastQueue: Greezer Denial: sending Intent { act=ACTION_POWER_CONNECTED ... }
>    due to receiver ProcessRecord{...} need cached broadcast
> ```
> App 在后台待久被冻住之后，动态注册的广播不投递（进程一起冻，连兜底轮询都停）。
> AOSP 的电池优化白名单 / standby bucket 都不够，**必须让用户在「应用信息 → 省电策略」里选「无限制」**
> （顺带把「自启动」「通知」也开上）。这条要写进给用户的说明里。

### 2. 检测「合盖了」

- 用 `Sensor.TYPE_HINGE_ANGLE`（铰链角度，0 ≈ 合上，180 ≈ 摊平）。
- **关键坑：它不是 wake-up 传感器。** 合盖之后屏幕熄灭、SoC 挂起，
  普通注册的传感器回调**不会把进程唤醒**。
  所以「常驻监听、等合盖事件」这种写法在真机上会经常哑火，尤其顺序是
  「先合盖、后插电」的时候。
- **正确做法**：把触发权交给插电广播（它会唤醒进程），然后**主动去要一次当前角度**——
  临时把注册频率提到 `SENSOR_DELAY_FASTEST`，拿到第一帧就判断，超时就用缓存值兜底，
  读完立刻降回 `SENSOR_DELAY_NORMAL`。

部分机型同时提供 `hinge_angle Non-wakeup` 和 `hinge_angle Wakeup` 两个实例
（`dumpsys sensorservice` 可查），但不要指望 `getDefaultSensor()` 一定给你 wakeup 那个。

> **v1.4.1 更新：铰链角度这条路最后被放弃了。**
> 在 Xiaomi 18 Fold（HyperOS / Android 17）上实测：手机合着的时候，
> `TYPE_HINGE_ANGLE` 会读到 **38~48°**（还在 ±2° 抖动），而 `foldAngleMax` 默认 30° ——
> 同一台手机，`dumpsys window` 里系统是 `mIsFolded=true / mDeviceState=FOLDED`，
> 本 App 却判成「已展开」，两套判定打架，结果就是**插电不亮、时好时坏**
> （刚合上时读到 3°，转个身再插电就变 38°+）。
>
> 改成问系统：**「现在亮着的这块屏是不是外屏」**。
> - 能看到两块屏时：面积大的那块是内屏，内屏不亮 ⇒ 合盖。
> - 折叠时 HyperOS 经常只把当前那块屏放进 App 的 `DisplayManager.getDisplays()`
>   （实测日志 `displays=0:ON`，内屏压根不在列表里）。这时按**尺寸**认：
>   外屏最小边 1168px ≈ 425dp，内屏 1672px ≈ 608dp，以 550dp 为界。
>
> 铰链现在只留在日志里当参考值（`hinge(参考)=`），不参与任何判定。

> **v1.4.2 又改一次：连「屏幕横竖」都不看了，改看手机姿态。**
> 外屏方向是「谁在前台谁说了算」——桌面这类竖屏锁定的界面在前台时，外屏永远停在
> `1168x1712 / rotation=0`，手机横着立在桌上也不会转（实测日志可查）。所以「屏幕不是横的
> 就不显示」会把最常见的两种使用姿态（A 字形 / L 字形立在桌上）全毙掉。
>
> - 判定改用加速度计重力方向：`|gy| ≥ |gx|` → 竖（0/180），否则横（90/270）；
>   `|gz| > 9.2` 且最大 → 平放，判不出来（-1，不显示）。
> - 姿态一变（400 ms 去抖）立刻回调服务重新判定：转到竖屏 / 放平 → 立刻收掉时钟。
> - 排版仍然只有横屏一套；屏幕被前台锁成竖屏时，把横屏尺寸的内容整体转 90°/270° 铺满。
> - **坑**：`Surface.ROTATION_*` 是枚举值 `0/1/2/3`，不是度数。直接拿它做角度减法，
>   差值算出来是 `1`，再被「必须是 90 的倍数」归零 → 舞台不转 → 屏幕上画出一个竖屏时钟。
>   必须先 `×90` 换算成度数。

### 3. 把界面亮出来 —— 真正的瓶颈

Android 10+ 有**后台启动 Activity（BAL）限制**。官方列的例外条件包含：

> The app has the SYSTEM_ALERT_WINDOW permission granted by the user.

也就是说 `startActivity()` 想从后台成功，必须有「悬浮窗」权限。但这只是 AOSP 这一层；
小米/HyperOS 还有专有的「后台弹出界面」开关，没开照样拦，而且不提供任何查询或申请 API。

**绕开方式**：直接把时钟做成 `TYPE_APPLICATION_OVERLAY` 悬浮窗。
「加一个悬浮窗」不属于「后台启动 Activity」，不受 BAL 约束，也不吃「后台弹出界面」那一套。

真要启动界面时，targetSdk 34+ 还有一个 AOSP 认可的写法（文档原文：creator 可以
「显式委托」自己的后台启动特权）：

```java
PendingIntent pi = PendingIntent.getActivity(ctx, 0, intent, FLAG_IMMUTABLE | FLAG_UPDATE_CURRENT);
Bundle opts = ActivityOptions.makeBasic()
        .setPendingIntentBackgroundActivityStartMode(
                ActivityOptions.MODE_BACKGROUND_ACTIVITY_START_ALLOWED)
        .toBundle();
pi.send(ctx, 0, null, null, null, null, opts);
```

本应用同时是 creator 和 sender，自己又持有 `SYSTEM_ALERT_WINDOW`，符合放行条件。

另注：targetSdk 35（Android 15）起，靠 `SYSTEM_ALERT_WINDOW` 这个例外去**启动前台服务**
还多一个条件——**必须当前真的有一个可见的悬浮窗**。Android 15 之前没有这条。

### 4. 长期有效

必须有开机恢复，否则一次重启就永久失效。`BootReceiver` 监听
`BOOT_COMPLETED` + `MY_PACKAGE_REPLACED` 即可。

注意：从 `BOOT_COMPLETED` 里启动前台服务是允许的（属于豁免情形），
但 Android 14+ 对某些 FGS 类型有额外限制；`specialUse` 不在受限列表里。

## 二、HyperOS 的外屏白名单

HyperOS 默认**不让随便什么应用跑到外屏上**，需要系统放行。
开源项目 [MixFlipMod](https://github.com/parallelcc/MixFlipMod)（面向小米 MIX Flip / Flip 2 的 Xposed 外屏增强模块）
的第一条功能就是「解除外屏应用限制」；**本项目用的是 18 Fold，但外屏白名单是 HyperOS 共用的一套属性**，
这个模块印证了机制。它 hook 的系统方法是：

```kotlin
val props = arrayOf("miui.continuity.policy",
                    "android.window.PROPERTY_COMPAT_ALLOW_SMALL_COVER_SCREEN")
// getPropertyIntByApplication 返回 5 / 1  →  所有应用都允许上外屏
```

顺着这条线索对系统做取证，得到的事实：

- `/system/framework/framework.jar` 里存在这些标识符：
  `COMPAT_SMALL_COVER_SCREEN_OPT_IN`、`android.window.PROPERTY_COMPAT_ALLOW_SMALL_COVER_SCREEN`、
  `miui.supportFlipFullScreen`、`com.miui.fliphome`（外屏桌面）。
- 扫描系统内 391 个 APK，找到真实声明样例。第三方应用照着**在 `<application>` 里声明**：

```xml
<property  android:name="android.window.PROPERTY_COMPAT_ALLOW_SMALL_COVER_SCREEN" android:value="1" />
<property  android:name="miui.continuity.policy"                                   android:value="5" />
<meta-data android:name="miui.supportFlipFullScreen"                               android:value="0" />
```

`miui.supportFlipFullScreen`：`0` = 全屏铺满，`1` = 不缩放，`2` = 自定义缩放。

实测结果：声明这三条之后，合盖时应用确实能显示在外屏上，且不需要开「后台弹出界面」。
（**未验证的部分**：无法完全排除这是 HyperOS 的默认行为而非这三行的作用；
也无法确认系统是否只对系统签名应用采纳这些属性。）

## 三、悬浮窗的几个坑

### 必须挂到「当前亮着的那块屏」

折叠时主屏是灭的，窗口要加到外屏上：

```java
DisplayManager dm = (DisplayManager) ctx.getSystemService(DISPLAY_SERVICE);
// 挑 STATE_ON 且非 FLAG_PRIVATE 的显示器
Context displayCtx = ctx.createDisplayContext(display);
WindowManager wm = (WindowManager) displayCtx.getSystemService(WINDOW_SERVICE);
wm.addView(view, params);
```

顺带一个实测现象：某机型合盖后会**把显示器编号对调**——合盖前
`display 0` 是内屏（1672×2364），合盖后 `display 0` 变成外屏（1168×1712），
内屏变成 `display 1` 且 `state OFF`。所以不要靠 displayId 判断哪块是哪块，
要用「当前 ON + 尺寸」。

### 窗口必须盖满整屏

只设 `MATCH_PARENT` + `FLAG_LAYOUT_IN_SCREEN` 还不够——系统会把状态栏/导航栏的 inset
从窗口高度里扣掉（1712 高只给到 1657），底下那一条盖不住，直接露出桌面。要显式声明
不参与 inset 计算：

```java
lp.setFitInsetsTypes(0);
lp.setFitInsetsSides(0);
```

### 判断屏幕横竖别用错 API

`Display.getWidth()` / `getHeight()` 返回的是**面板原始尺寸**，不随旋转变化。
外屏物理上是竖的（1168×1712），拿它判断会把外屏永远当成竖屏。
必须用 `Display.getSize(Point)` —— 它按当前旋转返回尺寸。

## 四、排版取舍

最终定稿：**只有一套横屏排版**（左时钟、右日历）。

| 外屏状态 | 行为 |
|---|---|
| 横屏 | 显示，铺满整屏 |
| 竖屏 | **什么都不显示** |

- 不维护竖屏上下堆叠那一套，省掉一份要调的比例。
- 竖屏不显示，也就不需要「把横屏内容转 90°」这种兜底。
- `MainActivity` 用 `SCREEN_ORIENTATION_SENSOR_LANDSCAPE`，系统只决定横屏的左右朝向。
- 悬浮窗跟着外屏旋转；服务注册 `DisplayManager.DisplayListener`，
  屏幕一转就重新判定——横过来立刻亮、竖过去立刻收。

日历部分的可调常量集中在 `CalendarPanelView` 顶部：

| 常量 | 值 | 含义 |
|---|---|---|
| `HEIGHT_BUDGET` | 0.60 | 日历内容块占所在面板高度的比例，其余留成黑边 |
| `PAD_RATIO` | 0.070 | 四周基础留白（相对面板短边） |
| `WIDTH_FACTOR` | 0.66 | 字号相对列宽的比例（保证两位数的「28」也放得下） |

另外日历**只画真正用得到的行数**（5 行或 6 行）。固定画 6 行的话，
遇到只需要 5 行的月份，最后一行整行都是下月日期，渲染成暗灰，视觉上就是底部一块空白。

## 五、代码里其他的坑

- **方向切换必须在 `onMeasure` 里做**，不能放 `onSizeChanged`。
  后者是布局**完成之后**才回调的，在那里改 `LayoutParams` 要多走一轮布局，实际不生效
  （曾经导致日历面板拿到 0 宽度，整块不显示）。
- **插电广播到达时不要回头读 sticky 的 `ACTION_BATTERY_CHANGED`**：
  广播先到、sticky 还没刷新，读到的可能是「没插电」的旧值，这一次就被判成未充电而错过。
  电源事件直接采信广播带来的状态。
- **判断「在充电」只认 `EXTRA_PLUGGED != 0`**，不要看 `EXTRA_STATUS == CHARGING/FULL`。
  那个状态位在拔线后可能残留，会导致「没插电也一直当成充电中」。
- **用户手动关掉之后要抑制重新弹出**，否则 20 秒一轮的兜底轮询会把它弹回来。
  只有插拔电、或折叠状态真的变化（展开↔合盖）才解除抑制。
- **`NotificationChannel.setLights(int,int,int)` 不存在**（是 `enableLights(boolean)`）。

## 六、构建

工程刻意做成**不需要 Gradle / Android Studio** 的形状：`AndroidManifest.xml + res/ + src/`，
用 `aapt2 / javac / d8 / apksigner` 四步直接编译。见仓库根的 `build.sh`。

几个注意点：

- 部分 Android 环境**没有 `zip`**，往 APK 里塞 `classes.dex` 要用 JDK 自带的 `jar ufM`。
- `javac -source 8 -target 8` 足够，代码里没有用任何 Java 8 以上的语法。
- 编译目标 `minSdk 32`；`d8 --min-api 32`。

## 十、v1.4.4：锁屏状态下的显示路径（2026-10-16）

目标场景：**锁屏 + 息屏 → 插电 → 屏幕亮起时，时钟盖在锁屏壁纸之上**。

三条路都做了实机取证，结论如下：

| 路径 | 结果 | 取证 |
|---|---|---|
| 悬浮窗 `TYPE_APPLICATION_OVERLAY` | ❌ 锁屏上画不出来 | 锁屏 + 息屏插电后窗口确实挂上了（`overlay=1`），但屏幕上是锁屏壁纸 + 充电动画，没有我们的时钟 |
| 全屏通知（`setFullScreenIntent`，系统闹钟机制） | ❌ 被 HyperOS 压住 | `canUseFullScreenIntent()=true`、通知确实发出、屏幕也被点亮，但 `isKeyguardShowing` 始终 true，界面上只有充电光效 |
| Activity + `showWhenLocked` | ✅ 能盖住锁屏 | 锁屏状态下启动 `MainActivity`：`isKeyguardShowing` 立刻变 false，全屏时钟出现 |
| ↳ 但"从后台启动 Activity" | ⚠️ 需要厂商开关 | 未授权时 `pi.send(...)` 不抛异常、界面就是不起来；对应 MIUI 的 `MIUIOP(10021)=ignore` |

**必须的两个 MIUI 权限**（实测编号）：

| 权限 | appop | 作用 |
|---|---|---|
| 后台弹出界面 | `10021` | 允许从后台把 Activity 拉到前台 |
| 锁屏显示 | `10020` | 允许内容显示在锁屏之上 |

打开后（`appop` 变 `allow`）实测：锁屏 + 息屏插电 → `MainActivity` 成为前台 → 全屏时钟盖在锁屏之上 ✓，
并且**连续多轮**都成立。

实现要点：

- 锁屏时**不挂悬浮窗**：它在锁屏之上画不出来，挂了只会在下面拉起的 Activity 之上再叠一个同样的时钟，
  两者排版差一两个像素 → 边缘出现重影/抖动。
- 锁屏时同时做两件事：发全屏通知（系统代启）+ 委托启动 Activity（`PendingIntent` +
  `MODE_BACKGROUND_ACTIVITY_START_ALLOWED`）。前者在部分 ROM 上"同一条通知重复 post 只算更新、
  不会再次触发"，所以不能只靠它 → 这正是"只成功一次"的元凶。
- 收起时钟时必须撤销那条全屏通知（`nm.cancel`），保证下次 post 是全新通知。
- `MainActivity` 带 `EXTRA_LOCKED` 启动：监听 `ACTION_USER_PRESENT`，用户一解锁就退场，
  不占着桌面；服务侧 `hide()` 通过 `ACTION_FINISH_UI` 广播也能让它退场（否则"服务认为已收起、
  屏幕上还留着全屏时钟"）。
- 自检面板新增 `LOCK popup=… screen=… fsi=…` 一行，直接反映这三项状态。
